## 3. 決定記録の形式

```markdown
### DEC-XX: 決定タイトル

- 状態: 決定済み
- 決定日: YYYY-MM-DD
- 決定: 選んだ内容
- 理由: 選定理由
- 影響: API、DB、画面、運用への影響
- 見直し条件: 判断を再検討する条件
```

大きな設計判断は `docs/decisions/` にADRとして分離できます。

## 4. 要件変更の流れ

1. 変更の背景と利用者価値を記録する
2. Phase、優先度、受け入れ条件を決める
3. 画面、API、DB、SEO、運用への影響を確認する
4. 関連文書を更新する
5. 実装Issueへ分割する
6. 実装・テスト・リリース後にチェックリストを更新する

## 5. 初回着手時の推奨タスク

1. DEC-01〜04、07、14を決定する
2. DBサービスと認証方式の小さな技術検証を行う
3. `.env.example`、DBスキーマ、マイグレーションscriptを追加する
4. 公開大会一覧APIの縦切り実装を行う
5. 非公開データが公開されない統合テストを最初に用意する
6. トップ・カレンダー・詳細を実装する
7. 認証と管理CRUDへ進む
